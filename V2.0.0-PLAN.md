# Agent Workshop v2.0.0 Modernization Plan

## Why

Agent Workshop was built when the Claude Agent SDK, OpenAI Agents SDK, and
HuggingFace tiny-agents were much less capable, and the generated code had to
compensate by hand-rolling file/command/web tools, permission systems, memory
loading, and subagent orchestration itself. Those SDKs have since matured
significantly and now provide most of that functionality natively.

The GitHub Copilot provider — added most recently — already demonstrates the
right pattern: **delegate to the SDK's built-ins, generate only what it
doesn't provide.** v2.0.0 brings the Claude, OpenAI, and HuggingFace providers
up to that same standard, so generated projects are:

- **Leaner** — far less boilerplate per generated project.
- **More current** — dependency pins reflect what the SDKs can do today.
- **More educational** — users see how to use the real SDK surface (built-in
  tools, native permission modes, first-class subagents/handoffs, sessions,
  tracing) instead of a custom workaround that obscures it.

This document is the working plan for that effort. Update it as phases land.

## Scope

Canonical generator: `agent-workshop-app/src/lib/generator.ts`
Mirror (must stay in sync per `CLAUDE.md`): `create-agent-app/src/generator/webapp-generator.ts`
Shared types: `agent-workshop-app/src/types/agent.ts`, `create-agent-app/src/types.ts`

Every phase below must be applied to **both** generator files (and both type
files, if the type model changes) before being considered complete.

## Validation checklist (run after every phase)

- [ ] `npm run type-check` (agent-workshop-app)
- [ ] `npm run lint` (agent-workshop-app)
- [ ] `npm run build` (create-agent-app)
- [ ] `npm run test:generator` — generator smoke test (tsx, no API keys needed)
- [ ] `npm run test:generator:all` — full generator matrix (no API keys needed)
- [ ] `npm run test:generator:build` for at least one affected provider — actually
      installs and builds a generated project
- [ ] `npm run test:agents:quick` — optional, only if live API keys are available
      in the environment; not required to consider a phase done

## Phase 0 — Critical / breaking fixes

**Status: not started**

Do this first — low risk, high value, and includes a live bug.

1. **Fix a live breaking bug:** generated OpenAI projects pin `"zod": "^3.0.0"`,
   but `@openai/agents` 0.4.0+ **requires Zod v4**. Any user who updates the
   OpenAI SDK today gets an immediate peer-dependency break. Bump generated
   `zod` pin to `^4.0.0` for OpenAI-provider projects.
2. Bump SDK pins in both generator files:
   - `@anthropic-ai/claude-agent-sdk`: `^0.1.53` → `^0.3.220`
   - `@openai/agents`: `^0.1.0` → `^0.13.5`
   - `@huggingface/mcp-client`: `^0.1.0` → `^0.2.3`
   - `@github/copilot-sdk` stays at `^1.0.8` (already current)
3. Remove the no-op `canUseTool` callback passed alongside `allowedTools` in
   the Claude provider path — as of SDK 0.3.198+ this combination emits a
   `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED` runtime warning.
4. Verify no generated code relies on the Claude SDK's V2 `createSession()`
   API, which was removed in 0.3.142 in favor of `continue` / `resume` /
   `fork` options on `query()`.

## Phase 1 — Stop hand-rolling file/command/web tools

**Status: not started**

The single biggest source of bloat: an estimated **~2,000 lines per generated
project** reimplement functionality both SDKs now ship natively.

### Claude provider

- Remove the generated `src/tools/file-operations.ts`, `command-runner.ts`,
  and `web-tools.ts` wrapper classes, and the `createSdkMcpServer` wrapper
  that hosts them as MCP tools, for the `file`/`command`/`web` categories.
- Replace with `allowedTools` passed directly to `query()`, drawn from the
  SDK's built-ins: `Read`, `Write`, `Edit`, `MultiEdit`, `Bash`, `Glob`,
  `Grep`, `WebSearch`, `WebFetch` — filtered by the wizard's tool selections.
- Generalize the existing `COPILOT_WRAPPER_TOOL_CATEGORIES` /
  `getCopilotExcludedTools()` pattern into a provider-keyed table (e.g.
  `SDK_NATIVE_TOOL_CATEGORIES`) so Claude takes the same code path Copilot
  already does.
- Knowledge-domain custom tools (via `tool()` + `createSdkMcpServer()`) are
  unaffected — only the file/command/web wrapper categories are removed.

### OpenAI provider

- Remove the axios + cheerio `web-tools.ts` wrapper; use `webSearchTool()` /
  `fileSearchTool()` from `@openai/agents`.
- Adopt the SDK's official `shellTool()` / `applyPatchTool()` adapters (added
  in 0.3.1) for command/file categories. These require a small user-supplied
  `shell` / `editor` glue implementation — much thinner than the current
  hand-rolled `CommandRunner`/`FileOperations` classes, and it's the
  officially documented pattern.
- Drop `axios` and `cheerio` from generated `package.json` once no longer
  referenced.

## Phase 2 — Replace hand-rolled permissions with SDK-native mechanisms

**Status: not started**

Current: a custom `PermissionManager` (~200 lines, regenerated per project)
implementing restrictive/balanced/permissive policies, its own CLI approval
prompts, and its own audit log.

- **Claude:** map the three policy levels onto native `permissionMode`
  presets (`restrictive` → `plan`/`dontAsk` + narrow `allowedTools`;
  `balanced` → `default` + `allowedTools`/`disallowedTools`; `permissive` →
  `acceptEdits`/`bypassPermissions`), plus an optional `PreToolUse` hook for
  audit logging — keeping the audit-log *concept* while dropping the custom
  approval logic around it.
- **OpenAI:** replace with per-tool `needsApproval`, `agent.inputGuardrails`
  / `outputGuardrails` for content-level checks, and the native
  `result.interruptions` / `RunState` pause-resume loop in the CLI for the
  user-facing approval prompt.
- **Copilot:** unchanged — already correctly uses `onPermissionRequest`.
- **HuggingFace:** likely keep the custom system (thinner native guardrail
  surface) — confirm during implementation.

## Phase 3 — Native subagents / handoffs instead of text injection

**Status: not started**

Current: subagent descriptions are injected as plain text into the system
prompt for both Claude and OpenAI — the model is just told it has helpers,
with no real delegation mechanism.

- **Claude:** use the `agents: { name: AgentDefinition }` option on `query()`
  (first-class since 0.3.x), with `"Agent"` included in `allowedTools`.
  Continue supporting filesystem-based `.claude/agents/*.md` definitions —
  the SDK honors both, with programmatic definitions winning on name
  collision.
- **OpenAI:** use `agent.handoffs` (specialist takes over the conversation)
  or `agent.asTool()` (manager stays in control and calls out) — see open
  question below on which should be the wizard default.

---

## Phase 4 — Memory / instructions loading cleanup

**Status: not started**

- **Claude:** remove the custom `claude-config.ts` CLAUDE.md/skills/commands
  reader — the SDK auto-loads all of these by default whenever
  `settingSources` isn't explicitly set to `[]`. This brings Claude in line
  with how Copilot already (correctly) does nothing here.
- **OpenAI:** no SDK auto-load exists, so keep a loader, but extract the
  duplicated logic into a single shared generated utility instead of two
  near-identical copies.

---

## Phase 5 — Sessions, streaming, tracing (OpenAI polish)

**Status: not started**

- Replace raw history-array prepending with the Sessions API
  (`MemorySession` for local/dev, optionally `OpenAIConversationsSession` for
  persistence).
- Enable `Runner({ workflowName })` so generated projects get free Tracing
  dashboard visibility with no extra code.
- Use real `run(agent, input, { stream: true })` in place of any fake stream
  currently synthesized from the final output (needs confirmation this
  exists before changing it).

---

## Phase 6 — Dependency and documentation cleanup

**Status: not started**

- Drop `axios`, `cheerio`, and any other now-unused dependencies from
  generated `package.json` once Phase 1 lands for both providers.
- Update root `CLAUDE.md` to describe the generalized "delegate to SDK
  built-ins" convention (currently documented as Copilot-only) so future
  contributors follow it for every provider.
- Update in-app docs (`agent-workshop-app/src/app/docs/`) and wizard copy to
  reflect what's now generated, leaning into "this shows you the real SDK
  surface" as the core educational value proposition.
- Audit the workshop app's own frontend dependencies for dead weight as a
  smaller, separate pass — out of scope for this plan unless it blocks the
  above.

---

## Sequencing

Phase 0 → Phase 1 → Phase 4 → Phase 2 → Phase 3 → Phase 5 → Phase 6.

Fix what's broken, kill the biggest bloat, do the easy cleanup, then the two
UX-sensitive changes (permissions, subagents), then polish.

## Open questions

1. **OpenAI subagents:** should wizard-configured "subagents" map to
   `handoffs` (specialist fully takes over the conversation) or `asTool()`
   (manager stays in control and just calls out to specialists)? This
   affects both the generated code shape and the wizard's subagent-step copy.
2. **OpenAI file/command tools:** is the SDK's official `shellTool()` /
   `applyPatchTool()` adapters — which still require a small user-supplied
   glue object — an acceptable trade vs. the newer `SandboxAgent` primitive
   (0.9.0+, full isolated workspace)? `SandboxAgent` is a bigger new template
   type and likely out of scope for this pass, but worth flagging as a
   possible v2.1+ direction.
3. **HuggingFace tiny-agents:** not yet part of the deep audit that produced
   this plan. Decide whether to fold it into v2.0.0 (needs its own research
   pass first) or leave it as-is for now, since its Node SDK surface for
   native permissions/tools is thinner than Claude's or OpenAI's.
4. **Permission vocabulary:** should the wizard keep presenting
   restrictive/balanced/permissive as the user-facing permission levels
   (just re-implemented on native mechanisms underneath), or is this a good
   moment to simplify/rename them to match each SDK's own vocabulary (e.g.
   Claude's `permissionMode` names) for clarity?
